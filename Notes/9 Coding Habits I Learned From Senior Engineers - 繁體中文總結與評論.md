## 📋 文章總結

這篇文章的核心觀點是：**資深與資淺工程師的差異不是速度，也不是懂更多語法、框架或技巧，而是「判斷力」（Judgment）**。

作者觀察資深工程師後發現，他們並不會急著動手寫程式碼：他們停頓得更久、問得更犀利、在「加東西」之前先「移除東西」，而且對命名的講究程度，一開始讓人覺得有點過頭——直到看見一個爛名字在後續造成多大的痛苦。

他們寫的不是「魔法般厲害」的程式碼，而是**別人可以安心修改**的程式碼。好程式碼不是「能動」的程式碼，而是「在產品改變、團隊擴大、期限提前、且深夜被別人 debug 時，依然撐得住」的程式碼。

以下是文章整理的九個習慣。

---

### 1. 先暫停，再開始（They Slow Down Before They Start）

資深工程師拿到 task 後，會先讀 ticket、看周遭的程式碼、問幾個問題，有時候花在「理解問題」上的時間比寫第一行程式碼還多。

乍看之下像是在「想太多」，但其實他們是在避免**假性進度（fake progress）**——寫程式碼會讓人有種「正在生產」的錯覺，但最快寫出來的程式碼，往往是之後最貴、最難撤銷的程式碼。

他們會問：這個功能真正的意思是什麼？誰依賴它？這是一次性規則，還是全新的產品行為？這個 edge case 是罕見狀況，還是這個領域本來就固有的一部分？

**核心思想**：先理解問題真正的形狀，程式碼自然就會變小。這個暫停能省下後面好幾個小時的工。

---

### 2. 保護「意義」，而非只是「語法」（They Protect Meaning, Not Just Syntax）

許多開發者整理程式碼時，只做「表面美化」：重新命名變數、搬動函式、拆檔案，讓東西「看起來」整齊。

資深工程師會往更深一層想：**這個「意義」到底該屬於哪裡？**

- 如果一個權限規則在三個元件裡重複出現，他們不會只因為 DRY 原則就直接抽一個 helper function，而是先問：這是 UI 關注點、後端關注點、政策（Policy）關注點，還是三者都是？
- 如果一條計費規則被藏在按鈕的 click handler 裡，他們不會只是重構這個 handler，而是把規則搬到它真正該屬於的 domain 層。

**核心思想**：Clean Code 不是「看起來整齊的程式碼」，而是「重要決策放在正確位置的程式碼」。當意義散落各處，系統會變得脆弱：每次改動都變成一場搜尋任務，每次修 bug 都變成一場猜謎遊戲。

---

### 3. 讓 State 變得無聊（They Make the State Boring）

State 是許多 bug 藏身之處：一個 loading flag、一個 selected item、Redux 裡的一個 filter、component 裡的 modal state、某處的 cache response，還有會同時影響同一張表格的 URL 參數……單獨看每一個都合理，全部加在一起就成了陷阱。

資深工程師不會問「這個資料可以存在哪裡？」，而是問：**「這個 state 該由誰擁有（Who owns this）？」**

- 有些 state 該放在 URL：因為使用者應該能重新整理或分享這個頁面
- 有些 state 該放在 component 內：因為沒有其他人需要用到它
- 有些 state 該是全域的：因為多個流程都依賴它
- 有些 state 根本不該存在：因為它其實可以被「推導」出來，不必額外儲存

**核心思想**：讓 state 變無聊——數量變少、命名清楚、所有權明確。無聊的 state，才是好的 state。

---

### 4. 為「下一次改動」而寫程式碼（They Write Code for the Next Change）

資深工程師不是要完美預測未來（那不可能），而是**避免把系統鎖死在「今天當下的形狀」**。他們知道產品需求很少一成不變：

一個狀態欄位最終會變成一整套工作流程；一個簡單的角色檢查最終會變成完整的權限模型；一顆小小的匯出按鈕最終會變成完整的報表需求；一份表單最終會變成很多份表單；一份寫死的清單最終會變成可設定的頁面。

他們選擇「能撐過成長」的命名，不把商業規則藏進 UI 元件裡，在「容易變動」的地方預留接縫（seam），讓 API 保持清楚，使其他開發者可以擴充而不必重寫一半的功能。

**核心思想**：這是一個難以拿捏的平衡——設計太少會產生雜亂的程式碼，設計太多會產生沒人敢碰的抽象程式碼。資深工程師活在中間地帶：為下一次改動而寫，但不會為它蓋一座城堡。

---

### 5. 把錯誤當作「產品行為」的一部分（They Treat Errors as Product Behavior）

很多人把錯誤處理當成任務的「收尾動作」：先做完 happy path，之後再補個提示訊息，也許處理一下 catch block，也許加個 log。

資深工程師把錯誤處理視為設計的一部分：API 失敗時應該發生什麼？使用者應該看到什麼？這個操作能不能重試？有沒有可能發生部分成功（partial success）？系統該 rollback、停用某個動作，還是保留舊有狀態？

**核心思想**：錯誤不只是技術問題，而是一種使用者體驗。儲存失敗不該讓使用者懷疑資料是否遺失；匯出失敗應該什麼都不做，而非留下半成品；權限檢查失敗不該看起來像頁面壞掉；網路請求失敗時，如果舊資料還有用，就不該把整個畫面摧毀。**Happy Path 只證明功能「能動」，Failure Path 才證明功能「準備好上線」。**

---

### 6. 避免「需要解釋」的聰明程式碼（They Avoid Clever Code That Needs Explaining）

寫出聰明的程式碼當下感覺很爽，換成別人要 debug 它的時候，感覺就沒那麼爽了。

一行聰明的程式碼可能藏著三個決策；一個泛用的抽象層可能藏著五種行為；一個「可重用」的 helper function，當沒人記得它包含哪些 edge case 時，反而變得危險。

資深工程師偏好「無聊但清楚」，勝過「聰明但精簡」。**簡單的程式碼不等於新手的程式碼，簡單的程式碼是尊重讀者的程式碼。**

**核心思想**：讓程式碼變短不代表讓它變好，讓程式碼變清楚才是變好。有時候，最好的版本是多寫幾行、把意圖攤開來寫清楚——畢竟程式碼被「讀」的次數遠比被「寫」的次數多，今天的聰明，是明天每一個讀者要付的代價。

---

### 7. 讓邊界保持「誠實」（They Keep Boundaries Honest）

資深工程師很在意邊界（Boundaries），而且是用很日常、很實際的方式在意：

他們會注意到 UI 元件什麼時候開始做商業決策；注意到 API Client 什麼時候開始格式化 domain 規則；注意到驗證邏輯什麼時候同時存在於三個地方；注意到一個 utility 檔案什麼時候變成什麼都塞的「雜物抽屜」；注意到後端 API 什麼時候對前端太過信任。

前端可以優化體驗，但後端必須強制執行規則；元件可以根據權限顯示或隱藏按鈕，但 API 仍然必須拒絕未授權的操作；表單可以驗證必填欄位，但伺服器仍然必須保護資料本身。

**核心思想**：當邊界薄弱，bug 會變得難以定位——一個行為壞掉了，卻沒人知道問題出在 component、hook、utility、API、資料庫，還是權限層。誠實的邊界讓系統有清楚的「責任歸屬」，讓 debug 更容易，也讓改動更安全。

---

### 8. 為「風險」做 Code Review，而非為「自尊」（They Review for Risk, Not Ego）

最好的 Code Review 不是為了展現優越感，而是為了**降低風險**。

資深工程師會問：這個條件為什麼存在？有沒有漏掉的 edge case？同樣的邏輯是不是已經在別的地方出現過？這個新的抽象層是否真的值得存在？這個改動會不會影響到匯出、權限、快取或分頁？

他們問的不是「這段程式碼漂不漂亮？」，而是：**「這段程式碼能不能安全地活在這個產品裡？」**

**核心思想**：好的 Code Review 不是為了抓誰的錯，而是為了保護整個 codebase，避免沒有人故意造成的錯誤發生。這代表 Review 時要看得比格式更遠——資料成長時會發生什麼？權限改變時會發生什麼？使用者行為出乎意料時會發生什麼？未來有人要擴充這個功能時又會發生什麼？

---

### 9. 讓程式碼庫比接手時更「平靜」（They Leave the Codebase Calmer Than They Found It）

資深工程師不是每次都做大重構，他們更常是「安靜地」改善系統：移除不必要的分支、重新命名一個令人困惑的函式、把一條規則搬到更好的位置、刪除死碼、簡化一個條件式、補上一個缺失的 guard、讓某個行為與其他地方更一致。

**核心思想**：程式碼庫不會靠一次「英雄式重構」變得可維護，而是靠「每天的紀律」累積出來的。每一個新功能，要嘛增加混亂、要嘛消除一些混亂；每一次修 bug，要嘛只是貼 OK 繃、要嘛讓行為更清楚；每一次 Review，要嘛放任複雜度通過、要嘛把它推向更好的形狀。不是每個任務都需要重構，但每個任務都是一個「減少一點摩擦」的機會。

---

### 對作者而言最大的轉變

作者最大的體悟是：資深工程能力不是一堆「進階技巧」的集合，而是一種**思考方式**。資深工程師不是永遠知道完美答案的人，而是在選擇答案之前，懂得先問更好的問題的人——關於「誰擁有這個」、關於「改動」、關於「失敗」、關於「下一個開發者」、關於「一個小決策會如何擴散到整個系統」。

這也是為什麼他們的程式碼感覺不一樣：不只是「更乾淨」，而是「更平靜（calmer）」。你可以不用猜測就讀懂它、可以放心地修改它、不用打開十個不相關的檔案就能 debug 它、可以相信重要的決策沒有被藏在隨機的地方。

> Junior 工程師常問：「這能動嗎？（Does this work?）」
> Senior 工程師常問：「這在未來還說得通嗎？（Will this still make sense later?）」
>
> 這一個問題的轉變，足以改變你寫程式碼的方式。

## 🎯 資深工程師評論

### 整體評價

這篇文章與同作者的《7 Coding Patterns I Stole From Senior Engineers》一脈相承，但切入點從「程式碼層級的技巧」提升到「工作方式與思維習慣」。九個習慣沒有一個是全新概念——問題釐清（Problem Framing）、State 的所有權（Single Source of Truth）、為改動而設計、防禦性邊界（Anti-Corruption Layer）、Blameless Review 文化，都是軟體工程界討論多年的主題。文章的價值在於把它們濃縮成「資深工程師實際上每天在做的動作」，用敘事方式讓讀者感同身受，而不是丟出一堆理論名詞。

---

### 值得肯定的地方

**第 1 條（先暫停）與第 9 條（讓程式碼庫更平靜）首尾呼應，點出了這篇文章真正的主軸：工程是一種長期紀律，而非單次的英雄行為。** 這個觀點比多數「程式碼技巧文」更有價值，因為它把焦點從「寫出來的程式碼長什麼樣子」，轉移到「工程師的工作習慣如何影響系統的長期健康」。

**第 3 條（讓 State 變得無聊）用「Who owns this」取代「Where can I store this」，是一個很精準的提問轉換。** 在前端狀態管理方案（Redux、Zustand、Context、URL、Server Cache）選擇過多的時代特別重要——很多團隊的痛點不是「沒有好用的工具」，而是沒人問過「這個 state 到底該誰負責」。

**第 5 條（把錯誤當作產品行為）呼應了近年「Error as UX」的趨勢**，尤其在強調產品體驗的團隊中，這個觀念比單純的例外處理更有說服力：錯誤處理的品質，直接反映在使用者對產品的信任感上。

---

### 可以更深入的地方

**第 2 條（保護意義）與第 7 條（誠實的邊界）其實是同一件事的兩種說法**，都在講「決策該放在正確的位置」。文章沒有明講的是，這兩者背後真正的理論基礎是 DDD 的 **Bounded Context** 與分層架構（Layered Architecture）。如果想把這個習慣系統化地落地，光靠「多想一下該放哪裡」是不夠的，還需要團隊有共識的分層規範（例如 Presentation / Application / Domain / Infrastructure），否則「意義該放哪裡」永遠只能靠個人經驗判斷，換一個資淺的人接手就會打回原形。

**第 6 條（避免聰明的程式碼）在實務上最大的挑戰，是「聰明」與「熟練」的界線很主觀。** 對資深工程師而言稀鬆平常的寫法（例如 LINQ 的鏈式操作、函式化的 Pattern、進階的 Pattern Matching），對團隊中較資淺的成員來說可能就是「需要解釋的聰明程式碼」。文章沒有處理這個落差——**「清楚」是相對於讀者的技術水平而定義的，不是一個絕對標準**，這代表資深工程師其實隱含了「了解你的團隊組成」這個前提，而不只是單純的程式碼風格選擇。

**第 8 條（為風險做 Review）如果沒有搭配團隊心理安全感（Psychological Safety），很容易變質。** 「問為什麼這個條件存在」立意良好，但如果 Review 文化本身充滿位階壓力，同樣的提問方式反而會被資淺工程師解讀為質疑或針對，變成另一種形式的「Ego Review」。文章談的是資深工程師「應該」怎麼做，卻沒有談團隊文化該如何配合，才能讓這種 Review 方式真正落地而不變調。

---

### 給台灣工程師的補充觀察

1. **「先暫停」在台灣高壓、快速交付的文化中特別難執行**——PM 催進度、Sprint 排得很滿的情況下，工程師常被迫「先寫了再說」。這篇文章其實也在提醒管理層：花在理解問題上的時間不是「沒進度」，而是在避免後面更貴的返工，這需要主管與團隊文化的配合，不能只靠工程師個人自律。
2. **第 3 條（State 的所有權）在中大型前端專案（尤其是電商後台、OMS/ERP 類系統）中特別容易失控**——一個篩選條件同時存在於 URL、Redux、Component State，還有 Server 端的 Session，四個地方互相打架的情況並不少見。這個習慣值得寫進團隊的 Frontend Code Review Checklist。
3. **第 9 條（讓程式碼庫更平靜）可以和「技術債」的溝通方式結合**：與其跟主管申請一大塊時間做重構，不如把這個習慣包裝成「每個 PR 都順手清理一點點」，這種顆粒度更容易在忙碌的商業節奏中被接受，也更符合台灣多數團隊「很難要到整塊重構時間」的現實。
