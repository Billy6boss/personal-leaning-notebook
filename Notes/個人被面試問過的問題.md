# 個人被面試問過的問題

## 1. AWS DDB 的索引有幾種? 分別是甚麼作用?

### 快速結論
DynamoDB 的存取路徑主要分成 **3 種**：

1. **Primary Key（主鍵）**：資料表本身內建的存取路徑，決定資料怎麼分區與排序
2. **Local Secondary Index（LSI，本地次要索引）**
3. **Global Secondary Index（GSI，全域次要索引）**

它們的共同目的都是：**讓你可以用「非主鍵」的欄位當條件查詢資料**。因為 DynamoDB 是 NoSQL，沒辦法像 SQL 一樣對任意欄位下 `WHERE` 條件查詢，那樣做等於是 Scan 全表，非常慢也非常貴，所以才需要靠這些索引設計不同的查詢路徑。

---

### 1️⃣ Primary Key（主鍵）
建表時一定要指定，有兩種形式：

| 類型 | 組成 | 說明 |
|------|------|------|
| **Simple Primary Key** | 只有 Partition Key（Hash Key） | 依 Partition Key 的雜湊值決定資料存在哪個實體分區，Key 值必須唯一 |
| **Composite Primary Key** | Partition Key + Sort Key（Range Key） | 同一個 Partition Key 下可以有多筆資料，依 Sort Key 排序，兩者合起來才唯一 |

範例：訂單表用 `CustomerId` 當 Partition Key、`OrderDate` 當 Sort Key，就能快速查出「某客戶的所有訂單，並依日期排序」。

---

### 2️⃣ Local Secondary Index（LSI）
**核心概念**：Partition Key 跟原表**相同**，只是換一個不同的 Sort Key 來查詢或排序。

- 只能在**建表當下**一起建立，事後**不能新增、刪除或修改**
- 跟原表**共用**同一個 Partition 的儲存空間與 RCU/WCU（讀寫吞吐量）
- 有一個重要限制：**同一個 Partition Key 底下，原表 + 所有 LSI 的資料總大小不能超過 10GB**，超過會導致該 Partition 寫入失敗
- 支援 **Strongly Consistent Read（強一致性讀取）**
- 一張表最多可以建立 **5 個 LSI**

**適合情境**：查詢範圍仍然限定在「同一個 Partition Key」內，只是想換個排序或過濾欄位。例如訂單表原本用 `OrderDate` 排序，想改成用 `Amount`（金額）排序，找出某客戶的高額訂單。

---

### 3️⃣ Global Secondary Index（GSI）
**核心概念**：等於是**另外開一張「虛擬表」**，可以用完全不同的 Partition Key（甚至加上不同的 Sort Key）來查詢整張表。

- 可以在**建表後任何時間**新增或刪除
- 有**自己獨立的 RCU/WCU**，不與原表共用（也代表要另外計費）
- 只支援 **Eventually Consistent Read（最終一致性）**，不支援強一致讀取，因為 GSI 的資料是透過非同步方式從原表複寫過來的（通常延遲很短，但終究不是即時）
- **沒有 10GB 大小限制**（底層儲存是分開的）
- 預設一張表最多 **20 個 GSI**（可以跟 AWS 申請調高配額）

**適合情境**：需要用完全不同的欄位查詢整張表。例如訂單表主要用 `CustomerId` 查詢，但想「查出某個商品被哪些訂單購買」，就可以建立一個以 `ProductId` 為 Partition Key 的 GSI。

---

### 補充：Projection（投影屬性）
不管是 LSI 還是 GSI，建立時都要決定「index 裡面要複製哪些欄位過去」：

| Projection Type | 說明 |
|------------------|------|
| **KEYS_ONLY** | 只投影 Partition Key / Sort Key，儲存成本最低，但查詢時常需要再回原表撈一次完整資料 |
| **INCLUDE** | 除了 Key 之外，額外指定要投影的欄位 |
| **ALL** | 投影所有欄位，查詢最方便，但儲存與寫入成本也最高 |

---

### 三者快速比較

| 比較項目 | Primary Key | LSI | GSI |
|----------|-------------|-----|-----|
| Partition Key | 自訂 | 與原表相同 | 可自訂（不同於原表） |
| Sort Key | 可選 | 不同於原表 | 可自訂 |
| 建立時機 | 建表時 | 只能建表時 | 隨時可新增/刪除 |
| 讀取一致性 | 強一致 / 最終一致皆可 | 強一致 / 最終一致皆可 | 只能最終一致 |
| 讀寫吞吐量 | 原表本身 | 與原表共用 | 獨立計費 |
| 大小限制 | 無特別限制 | 同一 Partition Key 下含原表共 10GB | 無限制 |
| 數量上限 | 1（表本身） | 5 個 | 20 個（可調） |

## 2. 問甚麼已經有 ASG 了，甚至是 Container Service (增長速度快)，為甚麼預期有高流量來臨還是要先預先加開機器?

### 核心結論
因為 **Auto Scaling 本質上是「反應式」（Reactive）而非「預測式」（Predictive）**：它一定要先偵測到「已經發生」的負載變化（CPU、Memory、Request Count 上升），才會觸發擴充動作。但從「偵測到」到「新資源真正能吃流量」中間，存在一連串**無法瞬間消除的延遲與物理限制**。如果流量是「已知、可預期、瞬間爆量」（例如促銷活動開賣、演唱會搶票、雙 11），這段延遲會直接反映成錯誤率上升與效能下降，所以才需要人為**提前**加開機器（Pre-scaling / Pre-warming）。

---

### 詳細原因

#### ① Scaling 本身就有偵測與冷卻延遲
- CloudWatch 等監控指標通常每 1～5 分鐘才聚合一次，就算用細顆粒度 Metrics 也還是有數十秒到一分鐘的延遲
- Scaling Policy 通常要「連續幾個週期超過門檻」才會觸發，避免誤判造成不必要的擴充
- 觸發後還有 **Cooldown Period**，避免短時間內重複擴充
- 這些加總起來，從「流量開始暴衝」到「Auto Scaling 決定要加機器」，往往已經過了好幾分鐘，這段時間現有資源可能早就被打爆了

#### ② 新資源「開起來」本身需要時間（冷啟動）
- **EC2**：開機 → 執行啟動腳本 → 部署應用程式 → 應用程式暖機（JIT 編譯、建立 DB Connection Pool、載入快取）→ 通過 Health Check 才會被 LB 導入流量
- **Container（ECS/EKS/K8s）**：雖然比 EC2 快，但仍需要 Pull Image（Image 較大時更明顯）、Container 啟動、應用程式初始化、通過 Readiness Probe
- 這些步驟少則幾十秒，多則好幾分鐘，在流量已經是「瞬間尖峰」的情況下，這段時間往往就是壓垮系統的關鍵

#### ③ 下游相依系統可能撐不住「瞬間湧入的新連線」
- 新開的機器/容器上線後，會**同時**去建立資料庫連線、連上快取、呼叫其他微服務
- 如果一次擴充很多台，可能瞬間對 DB 產生大量新連線，甚至超過資料庫的最大連線數上限，反而拖垮原本正常運作的下游服務
- 這是典型的「解決了前端問題，卻在後端產生新問題」

#### ④ 雪崩效應（Thundering Herd）
- 因為 Scaling 是「等到已經過載才觸發」，新機器一上線就要立刻面對**已經堆積的大量請求**
- 同時使用者端的重新整理、Client 端的自動重試，會讓請求量疊加得更高，形成惡性循環

#### ⑤ Auto Scaling 與底層資源都有速率與容量上限
- ASG 的 Step Scaling 通常有「一次最多加幾台」「多久內只能加一次」的限制
- 就算 Container Service 排程速度很快，底層 EC2 容量也可能不足，遇到 Insufficient Capacity Error（尤其是熱門機型或特定可用區）
- 也就是說，即使邏輯上「可以無限擴充」，實際上仍受限於雲端當下能提供的實體資源

#### ⑥ Load Balancer 自己也需要暖機
- ALB/NLB 背後其實也是由一組節點組成，會依流量緩慢自動擴充自身容量
- 如果流量是「瞬間」爆量而非平緩成長，LB 本身也可能來不及擴充，反而變成新的瓶頸
- 這也是為什麼 AWS 官方建議，若已知會有大流量事件（大型行銷活動、發表會），要**提前向 AWS Support 申請 ELB Pre-warming**

#### ⑦ 快取需要預熱，否則會有「Cache Miss Storm」
- 新開的機器、甚至是重啟後的快取節點，一開始都是空的（Cold Cache）
- 如果流量瞬間衝進來，大量請求都會 Cache Miss，直接打到資料庫，反而讓資料庫瞬間過載

#### ⑧ 有狀態（Stateful）服務無法像運算層一樣瞬間水平擴充
- ASG／Container 擴充的通常是**無狀態**的運算層（App Server）
- 但背後的資料庫、快取叢集等**有狀態服務**通常無法說擴就擴（需要資料同步、Replica 建立時間更長）
- 所以就算前端能快速擴充，後端資料層可能撐不住，必須提前手動擴容，例如先升級 DB 規格、增加 Read Replica

#### ⑨ 成本與風險的權衡
- 提前開機只是多付「短時間內」的機器費用
- 相較於尖峰時刻系統當機、訂單流失、商譽受損，這筆「保險費」其實相對便宜
- 這也是為什麼即使雲端強調彈性（Elasticity），大型電商或票務系統在「已知」的大型活動前，仍然會選擇人工介入，先行擴充、預熱，而不是完全信任 Auto Scaling 的即時反應

---

### 一句話總結
> Auto Scaling 解決的是「流量緩慢成長」的情境；但面對「已知、可預期的瞬間尖峰」，唯有靠**提前預測、提前擴充、提前預熱**，才能避免 Scaling 反應速度跟不上真實流量成長速度的問題。
