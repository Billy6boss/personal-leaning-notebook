# 《.NET 10 Minimal APIs + Reactive Programming》繁體中文總結與評論

> 原文：.NET 10 Minimal APIs + Reactive Programming

---

## 📋 文章總結

這篇文章的核心觀點是：**現代後端系統會垮，通常不是因為技術不夠新，而是因為架構的慣性（architectural inertia）——Controller 塞了太多責任、Service 之間綁得太死、交易橫跨太多系統。** 作者主張把 .NET 10 Minimal API 與 Reactive Programming（Rx.NET）結合，讓 HTTP 只是「事件的觸發點」，真正的業務邏輯搬到事件串流（Event Stream）裡運作，讓 Reactive Saga 在沒有中央協調器的情況下自然浮現。文章用一個簡化的訂餐外送（Tiffin）系統示範：下單 → 付款確認 → 備餐 → 派送，全部用事件反應串接起來。

---

### 1. Minimal API 帶來的不是語法糖，而是架構思維的轉變

Minimal API 常被介紹成「簡化版的 Controller」，但作者認為它其實是一種哲學轉變。Minimal API 具備幾個特質：Function-first、Stateless、Async-native、Streaming-friendly、不帶 MVC 的預設假設。最關鍵的一點是：**Minimal API 不鼓勵你做 Orchestration（集中式流程協調）**，這個特性剛好非常適合 Reactive／事件驅動架構。

**核心思想：Minimal API 的價值不在於少寫幾行程式碼，而在於它天生不誘導你把業務流程集中寫在一個地方。**

### 2. 從「請求驅動」走向「事件優先」

傳統模型的請求流程是線性、同步、綁死在 HTTP 上的：

```text
Request → Controller → Service Layer → Database → Response
```

這種模型的問題是：業務邏輯被綁在 HTTP 生命週期裡、長時間執行的流程被硬塞進同步呼叫、要擴充時只能整套一起複製。

Reactive + Minimal API 模型則是：

```text
HTTP → Event → Stream → Independent Reactions
```

HTTP 從此只扮演三個角色：傳輸邊界、觸發器（Trigger），但**不是**流程引擎。

**核心思想：HTTP 應該只負責「這件事發生了」，而不是負責「接下來要做哪些事」。**

### 3. Reactive Programming 的基礎：Observable、Observer、Subscription

.NET 的 Reactive Programming 由 Rx.NET（`System.Reactive`）驅動，核心概念是：

- **Observables**：事件的串流
- **Observers**：訂閱並反應事件的一方
- **Subscriptions**：動態建立的訂閱關係

**核心思想：我們不再「呼叫服務」，而是「對事實（Fact）做出反應」。**

### 4. 核心骨架：用一個 Subject 當作 Event Bus

範例專案刻意保持精簡（只有 `Program.cs` 一支檔案），核心是一個記憶體內的事件匯流排：

```csharp
var eventBus = new Subject<object>();
```

它同時扮演三個角色：事件發布者、扇出機制（Fan-out）、Saga 的骨幹。文章也明白指出，正式環境中這裡應該替換成 Kafka、Azure Event Hubs 或 RabbitMQ 之類的訊息系統，但整體概念不變。

### 5. Domain Event：用「事實」取代「命令」

系統中傳遞的是 immutable 的 record，代表「已經發生的事實」，而不是「要求做什麼」的命令：

```csharp
record OrderPlaced(Guid OrderId);
record PaymentConfirmed(Guid OrderId);
record MealPrepared(Guid OrderId);
record DeliveryAssigned(Guid OrderId);
record OrderFailed(Guid OrderId, string Reason);
```

這類事件具備 Immutable、Replayable、Auditable、Decoupled 四個特質。

**核心思想：命令告訴系統「該做什麼」，事件只陳述「發生了什麼」——事件驅動架構的解耦，正是從這個語意差異開始的。**

### 6. Minimal API 只負責「宣告」，不負責「執行」

下單端點刻意做得極簡：

```csharp
app.MapPost("/orders", () =>
{
    var id = Guid.NewGuid();
    eventBus.OnNext(new OrderPlaced(id));
    return Results.Accepted(id);
});
```

這個端點沒有商業邏輯、沒有呼叫其他服務、沒有寫資料庫。它唯一的責任是：**宣告「有這件事發生了」。**

### 7. 業務邏輯搬進 Reactive Pipeline

付款、備餐、派送分別是各自獨立的 Pipeline：

```csharp
// 付款 Pipeline
eventBus.OfType<OrderPlaced>()
    .Subscribe(e =>
    {
        Console.WriteLine($"Payment confirmed for {e.OrderId}");
        eventBus.OnNext(new PaymentConfirmed(e.OrderId));
    });

// 備餐 Pipeline（用 Delay 模擬處理時間）
eventBus.OfType<PaymentConfirmed>()
    .Delay(TimeSpan.FromSeconds(1))
    .Subscribe(e =>
    {
        Console.WriteLine($"Meal prepared for {e.OrderId}");
        eventBus.OnNext(new MealPrepared(e.OrderId));
    });

// 派送 Pipeline
eventBus.OfType<MealPrepared>()
    .Subscribe(e =>
    {
        Console.WriteLine($"Delivery assigned for {e.OrderId}");
        eventBus.OnNext(new DeliveryAssigned(e.OrderId));
    });
```

每個 Pipeline 都能獨立運作、獨立擴充、獨立失敗，彼此不需要知道對方的存在。

**核心思想：一條 Reactive Saga 不是被「設計」出來的流程圖，而是多個各自獨立的訂閱，因為訂閱了同一條事件鏈而自然串接起來。**

### 8. 沒有協調器的 Saga：失敗補償一樣用事件處理

失敗處理（Compensation）一樣是訂閱者：

```csharp
eventBus.OfType<OrderFailed>()
    .Subscribe(e =>
    {
        Console.WriteLine($"Refund issued for {e.OrderId}");
    });
```

整條鏈路裡沒有中央協調器、沒有 Workflow Engine、也沒有分散式交易，靠的是「向前推進 + 明確補償」的 Saga 精神。

### 9. 用 Minimal API + IAsyncEnumerable 做即時事件串流

```csharp
app.MapGet("/events", async IAsyncEnumerable<object> () =>
{
    var channel = Channel.CreateUnbounded<object>();
    var sub = eventBus.Subscribe(e => channel.Writer.TryWrite(e));

    await foreach (var e in channel.Reader.ReadAllAsync())
        yield return e;
    sub.Dispose();
});
```

這讓即時儀表板、內部觀察工具、除錯不再需要額外掛 Log，直接訂閱事件流即可。

## 🎯 資深工程師評論

### 整體評價

這篇文章的價值不在於介紹 Rx.NET 的 API（這些 API 已經存在很多年），而在於它把 Minimal API 的「輕量無主張」特性，跟 Reactive Programming 的「事件即事實」思維連在一起，示範了一種不靠 Workflow Engine、不靠分散式交易也能做出 Saga 的思路。對於習慣 Controller-Service-Repository 三層式架構的工程師來說，這是一個值得認真看一次的對照組。

### 值得肯定的地方

**把 HTTP 端點寫成「只宣告事實」是這篇文章最有價值的示範。** 很多系統的 Controller 或 Minimal API Handler 之所以越長越肥，就是因為工程師習慣性地把驗證、呼叫、寫入通通塞進同一個請求生命週期裡。這篇文章示範的 `app.MapPost("/orders", ...)` 只做一件事——發出 `OrderPlaced`——這個紀律其實比程式碼本身更值得學。

**用 immutable record 表達 Domain Event，而不是用 Command 物件**，這個選擇也點出了事件驅動系統設計的一個核心分野：Command 是「請求」，可能被拒絕；Event 是「事實」，已經發生就不能被否認。這個語意差異，決定了整個系統要怎麼做重播（Replay）、稽核（Audit）與除錯。

**強調「每個 Pipeline 可以獨立擴充、獨立失敗」**，這是 Reactive/Event-Driven 架構相較傳統三層式架構最實際的效益：Kitchen Pipeline 處理變慢，不會拖累 Payment Pipeline 的吞吐量，這在真正需要水平擴展的系統裡是關鍵優勢。

### 可以更深入的地方

**用記憶體內的 `Subject<object>` 當 Event Bus，只適合教學示範，不能直接套用到正式環境。** `Subject<object>` 沒有持久化、沒有 Replay 能力、也沒有 At-Least-Once 的傳遞保證——只要應用程式行程重啟，還沒被消費的事件就直接遺失。文章雖然有提到正式環境要換成 Kafka、Azure Event Hubs、RabbitMQ，但沒有進一步說明：換成這些系統之後，`OfType<T>().Subscribe(...)` 這種「同步、同行程內」的反應鏈，實務上會變成「跨行程、跨服務、非同步」的訊息消費者，這中間有相當大的工程落差，包括訊息序列化格式、消費者群組（Consumer Group）、訊息順序保證、重複消費（At-Least-Once）下的幂等性設計，這些都不是把 `Subject` 換成 `IMessageBroker` 介面就能自動解決的。

**這種「每個 Pipeline 訂閱上一個事件、再發布下一個事件」的做法，屬於 Choreography-based Saga（編舞式 Saga）**，跟傳統由中央 Coordinator 控制流程的 Orchestration-based Saga 是兩個不同派別，各有取捨。Choreography 的優點是去中心化、各步驟可以獨立部署與擴充；但當業務流程變複雜（例如超過 5、6 個步驟，或步驟之間有條件分支），「整個流程長什麼樣子」會分散在各處的 `Subscribe` 裡，沒有一個地方能一眼看出完整的流程圖，這會讓追蹤問題、設計逾時重試、畫出時序圖都變得困難，也是實務上 Choreography Saga 容易演變成「回呼義大利麵（Callback Spaghetti）」的常見風險，文章完全沒有討論這個取捨。

**文章示範的失敗補償過於簡化。** `OrderFailed` 的訂閱者只是印出一行「Refund issued」，但真正的 Saga 補償需要處理：如果訂單已經進行到「備餐」階段才失敗，要怎麼往回觸發「取消備餐」與「退款」兩個補償動作？如果同一個 `OrderFailed` 事件被重複消費兩次，會不會造成使用者被退兩次款（這就是幂等性 Idempotency 的問題）？這些才是 Saga 真正困難、也最容易出事故的地方，文章的範例並沒有觸及。

**`Subject<T>` 本身的執行緒安全與背壓（Backpressure）處理，這篇文章隻字未提。** `Subject` 在多執行緒同時呼叫 `OnNext` 時雖然不會拋例外，但訂閱者的執行順序與時機並沒有強保證；當事件產生速度超過訂閱者處理速度時（例如 Kitchen Pipeline 的 `Delay` 模擬慢速處理），沒有背壓機制的 in-memory Subject 可能會讓事件在記憶體中無限堆積。正式的訊息系統通常會提供流量控制或訂閱者端的 buffer/ack 機制，這是簡化範例特意忽略、但生產環境必須考慮的一塊。
